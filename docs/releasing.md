# Releasing openSzigno

This document describes how a release is cut, which workflow produces
which artefact, and what has to be configured once at the organisation
level before any of it works.

Everything except the final "publish the draft" click is automated. The
release archives, installers, and the Homebrew formula are generated by
[dist](https://github.com/axodotdev/cargo-dist) (formerly `cargo-dist`)
from `dist-workspace.toml`; the container image and the crates.io publish
are separate workflows triggered by the published release.

## What ships

| Artefact | Produced by | Where it lands |
| --- | --- | --- |
| `openszigno-cli-<target>.tar.gz` and `.zip` | `release.yml` | GitHub release assets |
| `sha256.sum` and one `.sha256` per archive | `release.yml` | GitHub release assets |
| `openszigno-cli-installer.sh` / `.ps1` | `release.yml` | GitHub release assets |
| `openszigno.rb` formula | `release.yml` | `watt-mind/homebrew-tap` |
| `source.tar.gz` | `release.yml` | GitHub release assets |
| `ghcr.io/watt-mind/openszigno` image | `container.yml` | GitHub Container Registry |
| `openszigno-core` and `openszigno-cli` crates | `publish-crates.yml` | crates.io |

Targets built for every release:

| Target | Runner |
| --- | --- |
| `x86_64-unknown-linux-musl` | GitHub-hosted Linux |
| `aarch64-unknown-linux-musl` | GitHub-hosted Linux |
| `x86_64-apple-darwin` | GitHub-hosted macOS |
| `aarch64-apple-darwin` | GitHub-hosted macOS |
| `x86_64-pc-windows-msvc` | GitHub-hosted Windows |

## Cutting a release

1. On a branch off `develop`, set the new version in the workspace
   `[workspace.package]` table, move the `CHANGELOG.md` `Unreleased`
   entries under the new version heading with its date, and update any
   version string in `README.md`. Open the pull request against
   `develop` as usual.
2. Once it is merged and CI is green on `develop`, open a pull request
   from `develop` to `master` and merge it. `master` is the stable
   branch and is what the tag points at.
3. Create the GitHub release as a **draft** on `master`, tagged
   `vX.Y.Z`, with the changelog section as the body. The workflow does
   not create the release: it expects the draft to exist, uploads the
   artefacts into it, and undrafts it only after every job has
   succeeded. `dist` 0.32 has no option that leaves a release drafted at
   the end of a run, so the human review happens on the draft body
   before the tag is pushed rather than after.
4. Push the tag. That starts `release.yml`.
5. Watch the run. The `custom-smoke-test` job unpacks the built
   `x86_64-unknown-linux-musl` archive and runs
   `openszigno inspect tests/fixtures/plain-base64.es3 --json` against
   it before anything is uploaded, so a binary that cannot read a
   synthetic dossier never reaches the release.
6. When `release.yml` finishes, the release is published. That fires
   `container.yml` and `publish-crates.yml`.
7. Check the results: the release page has the archives and installers,
   `watt-mind/homebrew-tap` has a new `Formula/openszigno.rb` commit,
   GHCR has the new image with its provenance attestation, and both
   crates are on crates.io.

## Publishing the draft by hand

If a job fails after the artefacts were uploaded, the release stays a
draft. Fix the cause, delete the tag and the draft, and start again from
step 3. To publish a draft that is known good without re-running the
workflow:

```sh
gh release edit v0.1.0 --draft=false
```

Publishing the draft by hand still fires `container.yml` and
`publish-crates.yml`, because both trigger on `release: published`.

## What each workflow does

| Workflow | Trigger | Does |
| --- | --- | --- |
| `release.yml` | push of a version tag; `pull_request` | Generated by `dist generate`. Plans, builds every target, builds installers and the formula, runs the smoke test, uploads to the draft release and undrafts it, then pushes the formula to the tap. On a pull request only the `plan` job runs (`pr-run-mode = "plan"`). |
| `smoke-test.yml` | called by `release.yml` | Reusable workflow. Downloads the built archives, unpacks the musl binary, and asserts that `inspect --json` reports `ok: true` on a synthetic fixture. |
| `container.yml` | `release: published` | Builds the `Dockerfile` for `linux/amd64` and `linux/arm64`, pushes `ghcr.io/watt-mind/openszigno` tagged with the tag, the bare version, and `latest`, then attests build provenance on the pushed digest. |
| `publish-crates.yml` | `release: published` | Verifies that the tag equals the workspace version, then publishes `openszigno-core` and `openszigno-cli` in that order. Skips with a notice when `CARGO_REGISTRY_TOKEN` is absent. |

Never hand-edit `.github/workflows/release.yml`. Change
`dist-workspace.toml` and regenerate:

```sh
cargo install cargo-dist --locked   # installs the `dist` binary
dist init --yes                     # or: dist generate
dist plan
```

## Testing a release without publishing one

Tag a release candidate. `dist` treats a version with a prerelease
suffix as a prerelease, so `latest` is not moved and the Homebrew
publish job skips itself.

```sh
git switch master && git pull
gh release create v0.2.0-rc.1 --draft --prerelease --notes "release candidate"
git tag v0.2.0-rc.1 && git push origin v0.2.0-rc.1
```

The workspace version has to match the tag for `publish-crates.yml`,
so an `-rc` tag that does not match is a deliberate way to exercise
everything except the crates.io publish. Delete the tag and the release
afterwards:

```sh
gh release delete v0.2.0-rc.1 --yes
git push origin --delete v0.2.0-rc.1
```

`dist plan` locally, and any pull request, exercise the planning stage
without touching a release at all.

## Required secrets and one-time setup

| Name | Kind | Used by | Needed for |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | automatic | `release.yml`, `container.yml` | Uploading assets and pushing to GHCR. Nothing to configure. |
| `HOMEBREW_TAP_TOKEN` | repository or organisation secret | `release.yml` | Pushing the formula to `watt-mind/homebrew-tap`. A fine-grained personal access token with `contents: write` on that repository, or a GitHub App installation token. |
| `CARGO_REGISTRY_TOKEN` | repository or organisation secret | `publish-crates.yml` | Publishing to crates.io. A crates.io API token scoped to `publish-new` and `publish-update`. |

One-time organisation setup:

- The tap repository `watt-mind/homebrew-tap` must exist and be public,
  with a `Formula/` directory. Homebrew resolves
  `watt-mind/tap/openszigno` to `github.com/watt-mind/homebrew-tap`, so
  the repository name has to be exactly `homebrew-tap`. The release job
  checks it out with `HOMEBREW_TAP_TOKEN`, commits
  `Formula/openszigno.rb`, and pushes to its default branch, so that
  branch must not require a pull request or a status check.
- The `openszigno-core` and `openszigno-cli` crate names must be owned
  by the account behind `CARGO_REGISTRY_TOKEN`. The first publish is
  what claims them.
- GHCR needs no repository beforehand. The first push creates the
  package; afterwards, set its visibility to public and link it to the
  repository in the organisation's package settings, otherwise
  `docker pull` requires authentication.

Without `HOMEBREW_TAP_TOKEN` the Homebrew publish job fails and the
release stays a draft; without `CARGO_REGISTRY_TOKEN` the crates job
skips itself and the release is unaffected.
