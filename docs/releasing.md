# Releasing openSzigno

This document describes how a release is cut, which workflow produces
which artefact, and what has to be configured once at the organisation
level before any of it works.

One human action starts a release and one ends it. Everything in between
is `.github/workflows/release.yml`, generated by
[dist](https://github.com/axodotdev/cargo-dist) (formerly `cargo-dist`)
from `dist-workspace.toml`. From 0.2.0 the crates.io publish and the
container build run **inside** that workflow as custom publish jobs, not
as separate workflows reacting to the published release. The reason is in
[Why nothing reacts to `release: published`](#why-nothing-reacts-to-release-published).

## What ships

| Artefact | Produced by | Where it lands |
| --- | --- | --- |
| `openszigno-cli-<target>.tar.gz` and `.zip` | `release.yml` | GitHub release assets |
| `sha256.sum` and one `.sha256` per archive | `release.yml` | GitHub release assets |
| `openszigno-cli-installer.sh` / `.ps1` | `release.yml` | GitHub release assets |
| `openszigno.rb` formula | `release.yml` | `watt-mind/homebrew-tap` |
| `source.tar.gz` | `release.yml` | GitHub release assets |
| `ghcr.io/watt-mind/openszigno` image | `release.yml` calling `container.yml` | GitHub Container Registry |
| `openszigno-core`, `openszigno-verify`, `openszigno-cli` crates | `release.yml` calling `publish-crates.yml` | crates.io |

Targets built for every release:

| `aarch64-apple-darwin` | GitHub-hosted macOS |
| `x86_64-pc-windows-msvc` | GitHub-hosted Windows |

## Cutting a release

### 1. Prepare the version on a branch off `develop`

Set the new version in the workspace `[workspace.package]` table, raise
the intra-workspace dependency requirements to match
(`openszigno-core = { version = "X.Y.Z", path = ... }` in the `verify` and
`cli` manifests, and `openszigno-verify` in the `cli` manifest), run
`cargo update --workspace` so `Cargo.lock` follows, move the
`CHANGELOG.md` `Unreleased` entries under the new version heading with its
date and compare links, and update every version string in `README.md` and
in the `Dockerfile` `VERSION` default. Open the pull request against
`develop` as usual.

### 2. Open the release pull request from `develop` to `master`

Once the version pull request is merged and CI is green on `develop`, open
a pull request from `develop` to `master` and merge it. `master` is the
stable branch and is what the tag points at.

### 3. Create the draft release, which also creates the tag

```sh
gh release create vX.Y.Z \
  --draft \
  --target master \
  --title "openSzigno X.Y.Z" \
  --notes-file notes.md
```

`--target master` makes `gh` create the tag `vX.Y.Z` on the tip of
`master` as part of creating the release, so there is no separate
`git tag` and `git push`. Creating the tag is what starts `release.yml`.
Put the `CHANGELOG.md` section for this version in `notes.md`.

The release must exist as a draft first: `create-release = false` in
`dist-workspace.toml`, so the workflow does not create the release. It
uploads the artefacts into the draft and undrafts it only after every job
has succeeded. dist 0.32 has no option that leaves a release drafted at
the end of a run, so the human review happens on the draft body before the
tag exists rather than after.

### 4. Watch the run

`release.yml` runs, in order:

| Job | Does |
| --- | --- |
| `plan` | Computes the release plan and hands it to every other job as a JSON string. |
| `build-local-artifacts` | Builds the binary and archive for each of the five targets. |
| `build-global-artifacts` | Builds the installers, the formula, the checksums, and the source tarball. |
| `custom-smoke-test` | Unpacks the built `x86_64-unknown-linux-musl` archive and runs `openszigno inspect tests/fixtures/plain-base64.es3 --json` against it, so a binary that cannot read a synthetic dossier never reaches the release. |
| `host` | Uploads everything into the draft release. |
| `publish-homebrew-formula` | Commits `Formula/openszigno.rb` to `watt-mind/homebrew-tap`. |
| `custom-publish-crates` | Publishes the three crates to crates.io. |
| `custom-container` | Builds and pushes the multi-arch GHCR image and attests its provenance. |
| `announce` | Undrafts the release. |

The three publish jobs run in parallel after `host`, and `announce` waits
for all of them, so the release only becomes visible once every channel
has actually published.

### 5. Check the results

The release page has the archives, checksums, and installers;
`watt-mind/homebrew-tap` has a new `Formula/openszigno.rb` commit; GHCR has
the new image with its provenance attestation; and all three crates are on
crates.io.

## Rerunning a failed publish job

The publish jobs are reusable workflows that also accept
`workflow_dispatch`, so a single failed channel can be rerun without
recutting the release. Both take a `tag` input:

```sh
gh workflow run publish-crates.yml -f tag=vX.Y.Z
gh workflow run container.yml -f tag=vX.Y.Z
```

Each job checks the tag out and works from that tree, so a manual rerun
publishes exactly what the release built. `publish-crates.yml` re-checks
that the tag equals the workspace version and skips with a notice if
`CARGO_REGISTRY_TOKEN` is absent; a crate that is already on crates.io
makes `cargo publish` fail, so rerun it only for a channel that genuinely
did not publish.

Rerunning `gh workflow run` from the branch picker uses the workflow file
on that branch. Run it from `master` after the release pull request has
merged, so the workflow definition matches the released tag.

If a job fails before `announce`, the release stays a draft. Fix the
cause, rerun the failed job, and let the run finish; or, if the draft is
known good and only the undraft is missing:

```sh
gh release edit vX.Y.Z --draft=false
```

That is now purely cosmetic. Nothing reacts to the release being
published any more.

## Why nothing reacts to `release: published`

Two separate GitHub behaviours make a `release: published` workflow the
wrong place for a publish step, and 0.1.0 hit both.

1. **Release-event workflows are read from the tagged commit.** For a
   `release` event GitHub loads the workflow files as they exist at the
   commit the release points at. The 0.1.0 tag predated
   `publish-crates.yml` and `container.yml`, so as far as GitHub was
   concerned those workflows did not exist and neither one was queued.
2. **`GITHUB_TOKEN` events do not trigger workflows.** Even on a tag that
   does contain the workflow files, dist undrafts the release with the
   automatic `GITHUB_TOKEN`. GitHub deliberately does not trigger further
   workflow runs from events raised by that token, precisely to avoid
   recursive runs. The `release: published` event fires, but nothing
   listens.

That is why **0.1.0 is on neither crates.io nor GHCR**: the release
archives, installers, and the Homebrew formula shipped, and the two
publish workflows simply never ran. 0.2.0 is the first release published
to crates.io and to GHCR, and the first with a Homebrew formula in the tap
that matches a published crate set.

The fix is structural: both publishes are now custom `publish-jobs`
entries in `dist-workspace.toml`, invoked by `release.yml` as reusable
workflows on the same run, before the release is undrafted. Nothing
depends on an event that a bot token raises.

## What each workflow does

| Workflow | Trigger | Does |
| --- | --- | --- |
| `release.yml` | creation of a version tag; `pull_request` | Generated by `dist generate`. Plans, builds every target, builds installers and the formula, runs the smoke test, uploads to the draft release, calls the three publish jobs, then undrafts. On a pull request only the `plan` job runs (`pr-run-mode = "plan"`). |
| `smoke-test.yml` | `workflow_call` from `release.yml` | Reusable workflow (`global-artifacts-jobs`). Downloads the built archives, unpacks the musl binary, and asserts that `inspect --json` reports `ok: true` on a synthetic fixture. |
| `publish-crates.yml` | `workflow_call` from `release.yml`; `workflow_dispatch` | Reusable workflow (`publish-jobs`). Checks that the tag equals the workspace version, then publishes `openszigno-core`, `openszigno-verify`, and `openszigno-cli` in that order with `cargo publish --locked`, relying on cargo's own wait for each crate to appear in the index. Skips with a notice when `CARGO_REGISTRY_TOKEN` is absent. |
| `container.yml` | `workflow_call` from `release.yml`; `workflow_dispatch` | Reusable workflow (`publish-jobs`). Checks the tag out, builds the `Dockerfile` for `linux/amd64` and `linux/arm64`, pushes `ghcr.io/watt-mind/openszigno` tagged with the tag, the bare version, and `latest`, then attests build provenance on the pushed digest. |

Both publish workflows take the same two inputs. `plan` is the dist plan
as a JSON string, which is what dist passes to a custom publish job; the
tag is read from its `announcement_tag` field. `tag` is optional on
`workflow_call` and required on `workflow_dispatch`, and overrides the
plan, which is what makes a manual rerun possible.

Never hand-edit `.github/workflows/release.yml`. Change
`dist-workspace.toml` and regenerate:

```sh
cargo install cargo-dist --locked   # installs the `dist` binary
dist init --yes                     # or: dist generate
dist plan
```

### Permissions

A reusable workflow can only narrow the token the caller hands it, so a
permission the caller does not grant cannot be recovered inside the called
workflow. dist gives custom publish jobs `id-token: write` and
`packages: write` by default, which is neither enough for the container
job (it also needs `contents: read` and `attestations: write`) nor right
for the crates job. Both are set at the caller through
`[dist.github-custom-job-permissions]` in `dist-workspace.toml`:

```toml
[dist.github-custom-job-permissions]
publish-crates = { contents = "read" }
container = { contents = "read", packages = "write", "id-token" = "write", attestations = "write" }
```

After changing that table, run `dist generate` and confirm the
`permissions:` block on `custom-publish-crates` and `custom-container` in
the regenerated `release.yml`. The job-level `permissions:` inside each
reusable workflow repeats the same set, which is what applies on a
`workflow_dispatch` rerun.

## Testing a release without publishing one

Tag a release candidate. `dist` treats a version with a prerelease suffix
as a prerelease, so `latest` is not moved, the Homebrew publish job skips
itself, and so do both custom publish jobs.

```sh
gh release create vX.Y.Z-rc.1 --draft --prerelease --target master \
  --notes "release candidate"
```

Delete the tag and the release afterwards:

```sh
gh release delete vX.Y.Z-rc.1 --yes
git push origin --delete vX.Y.Z-rc.1
```

`dist plan` locally, and any pull request, exercise the planning stage
without touching a release at all.

## Required secrets and one-time setup

| Name | Kind | Used by | Needed for |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | automatic | `release.yml`, `container.yml` | Uploading assets and pushing to GHCR. Nothing to configure. |
| `HOMEBREW_TAP_TOKEN` | repository or organisation secret | `release.yml` | Pushing the formula to `watt-mind/homebrew-tap`. A fine-grained personal access token with `contents: write` on that repository, or a GitHub App installation token. |
| `CARGO_REGISTRY_TOKEN` | repository or organisation secret | `publish-crates.yml` | Publishing to crates.io. A crates.io API token scoped to `publish-new` and `publish-update`. |

The generated caller passes `secrets: inherit`, so a repository or
organisation secret reaches both reusable workflows without being listed
per job.

One-time organisation setup:

- The tap repository `watt-mind/homebrew-tap` must exist and be public,
  with a `Formula/` directory. Homebrew resolves
  `watt-mind/tap/openszigno` to `github.com/watt-mind/homebrew-tap`, so
  the repository name has to be exactly `homebrew-tap`. The release job
  checks it out with `HOMEBREW_TAP_TOKEN`, commits
  `Formula/openszigno.rb`, and pushes to its default branch, so that
  branch must not require a pull request or a status check.
- The `openszigno-core`, `openszigno-verify`, and `openszigno-cli` crate
  names must be owned by the account behind `CARGO_REGISTRY_TOKEN`. The
  first publish is what claims them, and 0.2.0 is that first publish.
- GHCR needs no repository beforehand. The first push creates the
  package; afterwards, set its visibility to public and link it to the
  repository in the organisation's package settings, otherwise
  `docker pull` requires authentication.

A publish job that fails now keeps the release a draft, because
`announce` waits for all three. Without `CARGO_REGISTRY_TOKEN` the crates
job skips itself rather than failing, so the release still completes.
